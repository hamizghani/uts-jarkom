## 1. IPv6 (Kurose & Ross §4.3)

### 1.1 IPv6 datagram format
- Header **fixed 40 bytes** (32 bit per baris).
- Field header (urutan baris):
  - Baris 1: `ver` | `traffic class` | `flow label`
  - Baris 2: `payload length` | `next hdr` | `hop limit`
  - Baris 3–6: `source address` (**128 bit**)
  - Baris 7–10: `destination address` (**128 bit**)
  - Lalu `payload (data)`

### 1.2 Kenapa IPv6?
- Ruang alamat IPv4 32-bit sudah habis (*exhausted*).
- Header fixed → forwarding lebih cepat.
- **Flow label** untuk per-flow treatment.

### 1.3 Yang dihapus dibanding IPv4
- **Tidak ada checksum.**
- **Tidak ada fragmentation di router.**
- **Options** dipindahkan ke *extension headers* lewat field `next hdr`.

### 1.4 Transition IPv4 → IPv6
- **Dual stack** + **tunneling** (IPv6 datagram dibawa di dalam IPv4 datagram).
- Data adopsi di slide: **50.1% pengguna mengakses Google lewat native IPv6 pada 28 Mar 2026.**
- Slide mencatat: "The same CIDR notation is also used in IPv6".

### 1.5 Membaca & menyingkat alamat IPv6
- 128 bit = **8 grup (hextet) × 16 bit**, ditulis dalam hex.
- Contoh langkah:
  - **Full form:** `2001:0db8:0000:0000:0000:ff00:0042:8329`
  - ① Hapus leading zero: `2001:db8:0:0:0:ff00:42:8329`
  - ② Run nol terpanjang → `::`: `2001:db8::ff00:42:8329`
- **Expanding** = kebalikannya: isi `::` dengan grup `0000` sebanyak yang dibutuhkan sampai total 8 grup.
- **Aturan (RFC 5952):**
  - `::` hanya boleh **sekali** per alamat.
  - Pakai `::` pada **run nol terpanjang**; kalau seri → yang **paling kiri**.
  - **Jangan** pakai `::` untuk satu grup 0 tunggal.
  - Hex ditulis **lowercase**.
- **Latihan di slide:**
  | Input | Hasil |
  |---|---|
  | `2001:db8:0:0:1:0:0:1` | `2001:db8::1:0:0:1` (seri → leftmost) |
  | `2001:db8:0:1:1:1:1:1` | tidak berubah (hanya satu grup 0) |
  | `2001::1::5` | **invalid** (ambigu, dua `::`) |

## 2. DHCP — Dynamic Host Configuration Protocol

### 2.1 Dua pertanyaan tentang IP address
1. Bagaimana **host** mendapat IP address dalam networknya (host part)?
2. Bagaimana **network** mendapat IP address untuk dirinya (network part)? (→ bagian 3)

Host mendapat IP dengan:
- Di-hard-code sysadmin di config file (mis. `/etc/rc.config` di UNIX), atau
- **DHCP**: dapat alamat secara dinamis dari server, "plug-and-play".

### 2.2 Tujuan & sifat DHCP
- Host mendapat IP address dari network server secara dinamis saat "join" network.
- Bisa **renew lease** pada address yang dipakai.
- Memungkinkan **reuse address** (address hanya dipegang saat terhubung/on).
- Mendukung **mobile users** yang join/leave network.

### 2.3 DHCP overview (4 langkah)
1. Host broadcast **DHCP discover** *[optional]*
2. DHCP server balas **DHCP offer** *[optional]*
3. Host meminta IP: **DHCP request**
4. DHCP server mengirim address: **DHCP ack**

Dua langkah pertama (discover & offer) bisa **dilewati** "if a client remembers and wishes to reuse a previously allocated network address" [RFC 2131].

### 2.4 Skenario client-server (slide 4-8)
- Topologi: DHCP server **223.1.2.5**. Router punya interface 223.1.1.4 (subnet 223.1.1.x: host .1, .2, .3), 223.1.2.9 (subnet 223.1.2.x: host .1, .2, dan server .5), 223.1.3.27 (subnet 223.1.3.x: host .1, .2).
- Biasanya DHCP server **co-located di router**, melayani semua subnet yang terhubung ke router.
- Arriving DHCP client butuh address di network ini.

### 2.5 Pertukaran pesan (slide 4-9) dengan field
| Pesan | src | dest | yiaddr | transaction ID | lifetime |
|---|---|---|---|---|---|
| **DHCP discover** ("is there a DHCP server out there?") | 0.0.0.0, 68 | 255.255.255.255, 67 | 0.0.0.0 | 654 | — |
| **DHCP offer** ("I'm a DHCP server! Here's an IP address you can use") | 223.1.2.5, 67 | 255.255.255.255, 68 | 223.1.2.4 | 654 | 3600 secs |
| **DHCP request** ("OK. I would like to use this IP address!") | 0.0.0.0, 68 | 255.255.255.255, 67 | 223.1.2.4 | 655 | 3600 secs |
| **DHCP ACK** ("OK. You've got that IP address!") | 223.1.2.5, 67 | 255.255.255.255, 68 | 223.1.2.4 | 655 | 3600 secs |

- Semua pesan **broadcast** (dest 255.255.255.255). Port server = **67**, port client = **68** (UDP).
- Transaction ID discover/offer = 654; request/ACK = 655.

### 2.5b DHCP: lebih dari sekadar IP address
DHCP juga bisa mengembalikan:
- Address **first-hop router** untuk client
- **Nama dan IP address DNS server**
- **Network mask** (menunjukkan bagian network vs host dari address)

### 2.6 DHCP example (slide 4-11, 4-12)
- Laptop yang connect memakai DHCP untuk mendapat IP address, address first-hop router, address DNS server.
- **DHCP REQUEST** di-encapsulate: DHCP → UDP → IP → Ethernet.
- Ethernet frame di-**broadcast** (dest: `FFFFFFFFFFFF`) di LAN, diterima router yang menjalankan DHCP server (router dengan DHCP server built-in; di gambar address 168.1.1.1).
- Ethernet di-demux ke IP, IP di-demux ke UDP, UDP di-demux ke DHCP.
- DHCP server membuat **DHCP ACK** berisi: IP address client, IP address first-hop router untuk client, nama & IP address DNS server.
- Reply ter-encapsulate diteruskan ke client, di-demux ke DHCP di client.
- Client sekarang tahu: IP-nya, nama & IP DNS server, IP first-hop router.

## 3. IP addressing: dapat subnet, hierarchical addressing, ICANN

### 3.1 Bagaimana network mendapat subnet part?
- **A:** mendapat alokasi sebagian dari **address space ISP provider**-nya.
- Contoh (slide 4-13): ISP's block `11001000 00010111 00010000 00000000` = **200.23.16.0/20**. ISP mengalokasikan menjadi 8 blok /23:

| Organization | Binary | Prefix |
|---|---|---|
| Org 0 | 11001000 00010111 0001**000**0 00000000 | 200.23.16.0/23 |
| Org 1 | 11001000 00010111 0001**001**0 00000000 | 200.23.18.0/23 |
| Org 2 | 11001000 00010111 0001**010**0 00000000 | 200.23.20.0/23 |
| ... | ... | ... |
| Org 7 | 11001000 00010111 0001**111**0 00000000 | 200.23.30.0/23 |

(Slide menulis biner penuh 8 bit pada oktet ketiga: 00010000, 00010010, 00010100, ..., 00011110.)

### 3.2 Hierarchical addressing: route aggregation (slide 4-14)
- **Fly-By-Night-ISP** mengiklankan ke Internet: "Send me anything with addresses beginning **200.23.16.0/20**" (meliputi Org 0–7: 200.23.16.0/23, 200.23.18.0/23, ..., 200.23.30.0/23).
- **ISPs-R-Us** mengiklankan: "Send me anything with addresses beginning **199.31.0.0/16**".
- Hierarchical addressing → **advertisement routing info efisien**.

### 3.3 More specific routes (slide 4-15, 4-16)
- **Organization 1 pindah** dari Fly-By-Night-ISP ke ISPs-R-Us (tetap pakai 200.23.18.0/23).
- ISPs-R-Us sekarang mengiklankan **route yang lebih spesifik**: "**199.31.0.0/16 or 200.23.18.0/23**".
- Fly-By-Night-ISP tetap mengiklankan 200.23.16.0/20. Router Internet memakai **longest prefix match** → traffic ke 200.23.18.0/23 lewat ISPs-R-Us. **[Catatan]** (mekanisme longest-prefix dibahas di materi router sebelumnya; slide hanya menunjukkan "more specific route").

### 3.4 IP addressing: last words (slide 4-17)
- ISP dapat blok address dari **ICANN** (Internet Corporation for Assigned Names and Numbers, icann.org):
  - Mengalokasikan IP address lewat **5 regional registries (RRs)** (yang bisa mengalokasikan lagi ke local registries).
  - Mengelola **DNS root zone**, termasuk delegasi manajemen tiap TLD (.com, .edu, ...).
- Cukupkah address 32-bit? ICANN mengalokasikan **chunk terakhir IPv4 ke RRs pada 2011**. **NAT** membantu mengatasi exhaustion; **IPv6** punya address space 128-bit.
- Kutipan Vint Cerf (soal keputusan membuat IPv4 32-bit): *"Who the hell knew how much address space we needed?"*

## 4. NAT — Network Address Translation

### 4.1 Ide dasar
- **Semua device di local network berbagi hanya satu IPv4 address** dari sudut pandang dunia luar.
- Contoh (slide 4-19): local network (mis. home network) **10.0.0/24**; host 10.0.0.1, 10.0.0.2, 10.0.0.3; interface router sisi lokal **10.0.0.4**; interface sisi WAN **138.76.29.7**.
- **Semua datagram yang keluar** dari local network punya **source NAT IP address yang sama (138.76.29.7)** tetapi **source port number berbeda**.
- Datagram dengan source/destination di dalam network lokal memakai alamat 10.0.0/24 (seperti biasa).

### 4.2 Private address space & keuntungan (slide 4-20)
- Semua device lokal punya address 32-bit di **private IP address space**: **10/8, 172.16/12, 192.168/16** — hanya boleh dipakai di local network.
- Keuntungan:
  - Hanya perlu **satu IP address** dari ISP untuk semua device.
  - Bisa **mengubah address host lokal** tanpa memberi tahu dunia luar.
  - Bisa **ganti ISP** tanpa mengubah address device lokal.
  - **Security:** device di dalam tidak langsung dapat dialamati / terlihat dari luar.

### 4.3 Implementasi: NAT router harus (transparan) (slide 4-21)
1. **Outgoing datagram:** ganti (source IP, port #) → (**NAT IP address, new port #**). Remote client/server akan membalas ke (NAT IP, new port #).
2. **Ingat** (di **NAT translation table**) setiap pasangan translasi (source IP, port #) ↔ (NAT IP, new port #).
3. **Incoming datagram:** ganti (NAT IP, new port #) di field destination dengan (source IP, port #) yang tersimpan di tabel.

### 4.4 Contoh langkah (slide 4-22)
1. Host **10.0.0.1** kirim datagram ke **128.119.40.186, 80**: `S: 10.0.0.1, 3345` → `D: 128.119.40.186, 80`.
2. NAT router ganti source address dari `10.0.0.1, 3345` menjadi `138.76.29.7, 5001`, **update tabel**.
   - **NAT translation table:** WAN side addr = `138.76.29.7, 5001` ↔ LAN side addr = `10.0.0.1, 3345`.
   - Datagram keluar: `S: 138.76.29.7, 5001` / `D: 128.119.40.186, 80`.
3. Reply tiba: `S: 128.119.40.186, 80` / `D: 138.76.29.7, 5001`.
4. NAT router mengganti destination menjadi `10.0.0.1, 3345` → `S: 128.119.40.186, 80` / `D: 10.0.0.1, 3345` diteruskan ke host.

### 4.5 Kontroversi NAT (slide 4-23)
- Kritik:
  - Router "seharusnya" hanya memproses sampai **layer 3**.
  - Masalah kekurangan address "seharusnya" diselesaikan oleh **IPv6**.
  - **Melanggar end-to-end argument** (manipulasi port # oleh network-layer device).
  - **NAT traversal:** bagaimana jika client ingin connect ke server di belakang NAT?
- Tapi **NAT akan tetap ada**: dipakai luas di home & institutional nets, **4G/5G cellular nets**.

## 5. Generalized Forwarding

### 5.1 Match plus action (slide 4-25)
- Review: tiap router punya **forwarding table** (alias **flow table**).
- Abstraksi **"match plus action"**: cocokkan bit pada packet yang datang, lalu lakukan action.
  - **Destination-based forwarding:** forward berdasarkan destination IP address.
  - **Generalized forwarding:**
    - Banyak **header field** dapat menentukan action.
    - Banyak **action** mungkin: **drop / copy / modify / log** packet.

### 5.2 Flow table abstraction (slide 4-26, 4-27)
- **Flow:** didefinisikan oleh nilai header field (di field link-, network-, transport-layer).
- **Generalized forwarding:** aturan penanganan packet yang sederhana:
  - **match:** pola nilai pada header field packet
  - **actions:** untuk matched packet: **drop, forward, modify**, atau **kirim matched packet ke controller**
  - **priority:** membedakan pola yang overlap
  - **counters:** #bytes dan #packets
- Flow table router mendefinisikan aturan match+action router.
- **Contoh flow table** (router dengan 4 port; `*` = wildcard):
  | Match | Action |
  |---|---|
  | `src = *.*.*.*, dest = 3.4.*.*` | `forward(2)` |
  | `src = 1.2.*.*, dest = *.*.*.*` | `drop` |
  | `src = 10.1.2.3, dest = *.*.*.*` | `send to controller` |

### 5.3 OpenFlow: flow table entries (slide 4-28)
Setiap entry = **Match | Action | Stats**.
- **Stats:** packet + byte counters.
- **Action:**
  1. Forward packet to port(s)
  2. Drop packet
  3. Modify fields in header(s)
  4. Encapsulate and forward to controller
- **Header fields to match:**
  - Link layer: Ingress Port, Src MAC, Dst MAC, Eth Type, VLAN ID, VLAN Pri
  - Network layer: IP Src, IP Dst, IP Proto, IP ToS
  - Transport layer: TCP/UDP Src Port, TCP/UDP Dst Port

### 5.4 OpenFlow examples (slide 4-29, 4-30)
Urutan kolom match: Switch Port, MAC src, MAC dst, Eth type, VLAN ID, VLAN Pri, IP Src, IP Dst, IP Prot, IP ToS, TCP s-port, TCP d-port → Action. (`*` = wildcard.)

| Jenis | Aturan | Match (field yang tidak wildcard) | Action |
|---|---|---|---|
| **Destination-based forwarding** | IP datagram dengan tujuan 51.6.0.8 di-forward ke router output port 6 | IP Dst = 51.6.0.8 | `port6` |
| **Firewall (blok ssh)** | Blok semua datagram ke TCP port 22 (ssh) | TCP d-port = 22 | `drop` |
| **Firewall (blok host)** | Blok semua datagram yang dikirim host 128.119.1.1 | IP Src = 128.119.1.1 | `drop` |
| **Layer 2 destination-based forwarding** | Frame layer 2 dengan MAC tujuan 22:A7:23:11:E1:02 di-forward ke output port 3 | MAC dst = 22:A7:23:11:E1:02 | `port3` |

### 5.5 OpenFlow abstraction: menyatukan berbagai device (slide 4-31)
| Device | Match | Action |
|---|---|---|
| **Router** | longest destination IP prefix | forward out a link |
| **Switch** | destination MAC address | forward or flood |
| **Firewall** | IP addresses and TCP/UDP port numbers | permit or deny |
| **NAT** | IP address and port | rewrite address and port |

### 5.6 OpenFlow example: network-wide behavior (slide 4-32, 4-33)
**Topologi:**
- Hosts: h1 = 10.1.0.1, h2 = 10.1.0.2 (di s1); h3 = 10.2.0.3, h4 = 10.2.0.4 (di s2); h5 = 10.3.0.5, h6 = 10.3.0.6 (di s3). Ada OpenFlow controller yang terhubung ke switch.
- **s3:** port 1 → h6, port 2 → h5, port 3 → s1, port 4 → s2.
- **s1:** port 1 ← s3, port 2 → h1, port 3 → h2, port 4 → s2.
- **s2:** port 1 ← s3, port 2 ← s1, port 3 → h3, port 4 → h4.
- (Detail koneksi port ini **[Diturunkan]** dari gambar & tabel; konsisten dengan flow table di bawah.)

**Tujuan:** datagram dari h5 dan h6 harus dikirim ke h3 atau h4, **lewat s1** dan dari sana ke s2.

**Flow table per switch:**
| Switch | Match | Action |
|---|---|---|
| **s3** | IP Src = 10.3.\*.\*, IP Dst = 10.2.\*.\* | forward(3) |
| **s1** | ingress port = 1, IP Src = 10.3.\*.\*, IP Dst = 10.2.\*.\* | forward(4) |
| **s2** | ingress port = 2, IP Dst = 10.2.0.3 | forward(3) |
| **s2** | ingress port = 2, IP Dst = 10.2.0.4 | forward(4) |

Jalur: h5/h6 → s3 (port 3) → s1 (masuk port 1, keluar port 4) → s2 (masuk port 2, keluar port 3 ke h3 atau port 4 ke h4).

### 5.6b Generalized forwarding: summary (slide 4-34)
- Abstraksi "match plus action": match bit pada header packet di **layer mana pun**, lalu lakukan action.
  - Matching atas banyak field (link-, network-, transport-layer).
  - Local actions: drop, forward, modify, atau kirim matched packet ke controller.
  - "Program" perilaku network-wide.
- Bentuk sederhana dari **"network programmability"**:
  - Programmable, per-packet "processing"
  - Akar historis: **active networking**
  - Hari ini: pemrograman yang lebih general: **P4** (p4.org).

## 6. Middleboxes

- Definisi (RFC 3234): **"any intermediary box performing functions apart from normal, standard functions of an IP router on the data path between a source host and destination host."**
- **Middleboxes everywhere** (slide):
  | Fungsi | Lokasi/pengguna |
  |---|---|
  | **NAT** | home, cellular, institutional |
  | **Firewalls, IDS** | corporate, institutional, service providers, ISPs |
  | **Load balancers** | corporate, service provider, data center, mobile nets |
  | **Caches** | service provider, mobile, CDNs |
  | **Application-specific** | service providers, institutional, CDN |
- **Evolusi middleboxes:**
  - Awalnya: solusi hardware **proprietary (closed)**.
  - Bergerak ke hardware **"whitebox"** yang mengimplementasikan **open API**; menjauh dari hardware proprietary.
  - **Programmable local actions** lewat match+action.
  - Inovasi/diferensiasi bergeser ke **software**.
  - **SDN:** kontrol & manajemen konfigurasi (logis) terpusat, sering di private/public cloud.
  - **NFV (network functions virtualization):** layanan terprogram di atas white box networking, computation, storage.

## 7. Internet Architecture

### 7.1 IP hourglass (slide)
- **Thin waist = IP**: satu protokol network layer yang **harus diimplementasikan semua (miliaran) device** yang terhubung Internet.
- Banyak protokol di atas dan di bawahnya:
  - Application: HTTP, SMTP, DASH, ...
  - Transport: TCP, UDP, QUIC, RTP, ...
  - Link: Ethernet, WiFi, Bluetooth, PPP, PDCP, ...
  - Physical: copper, radio, fiber
- **"IP hourglass at middle age"**: ada "love handles" = **middleboxes** (mis. firewalls, caching) yang beroperasi di dalam network.

### 7.2 Architectural principles (RFC 1958)
Kutipan inti: *"...the goal is connectivity, the tool is the Internet Protocol, and the intelligence is end to end rather than hidden in the network."*

**Tiga keyakinan inti:**
1. **Simple connectivity**
2. **IP protocol: that narrow waist**
3. **Intelligence, complexity at network edge**

### 7.3 The end-end argument
- Sebagian fungsi network (mis. **reliable data transfer, congestion control**) bisa diimplementasikan **di dalam network** atau **di network edge**:
  - **End-end implementation** of reliable data transfer: di layer transport antar dua end host.
  - **Hop-by-hop (in-network) implementation:** di layer network tiap router/hop.
- Kutipan Saltzer, Reed, Clark (1981): fungsi tersebut **hanya dapat diimplementasikan dengan lengkap dan benar dengan pengetahuan dan bantuan aplikasi di end point**; menyediakan fungsi itu sebagai fitur sistem komunikasi itu sendiri **tidak mungkin** secara lengkap. (Kadang versi tidak lengkap dari fungsi itu di sistem komunikasi berguna sebagai **performance enhancement**.) Argumen melawan implementasi fungsi di level rendah ini disebut **"end-to-end argument"**.

### 7.4 Where's the intelligence?
| Era | Letak intelligence |
|---|---|
| **20th century phone net** | intelligence/computing di **network switches** (telepon "bodoh") |
| **Internet (pre-2005)** | intelligence, computing di **edge** |
| **Internet (post-2005)** | **programmable network devices**; intelligence, computing, infrastruktur application-level masif di **edge** |

## 8. Slide tambahan (Additional Chapter 4 slides)

### 8.1 IP fragmentation/reassembly (slide 4-47, 4-48)
- Network links punya **MTU** (max. transfer size) = frame link-level terbesar. Link type berbeda → MTU berbeda.
- Datagram IP besar **dipecah ("fragmented")** di dalam net:
  - Satu datagram menjadi beberapa datagram.
  - **"Reassembled" hanya di destination.**
  - Bit IP header dipakai untuk mengidentifikasi & mengurutkan fragmen terkait.
- **Contoh:** datagram **4000 byte**, **MTU = 1500 byte**.

| Fragmen | length | ID | fragflag | offset |
|---|---|---|---|---|
| Datagram asli | 4000 | x | 0 | 0 |
| Fragmen 1 | 1500 | x | 1 | 0 |
| Fragmen 2 | 1500 | x | 1 | 185 |
| Fragmen 3 | 1040 | x | 0 | 370 |

- Tiap fragmen penuh membawa **1480 byte data** (1500 − header 20 byte); **offset = 1480/8 = 185** (offset dalam satuan 8 byte); fragmen 2 → 2960/8 = 370 untuk fragmen 3. fragflag = 1 berarti "masih ada fragmen berikutnya"; fragmen terakhir fragflag = 0.
- **[Diturunkan]** Data fragmen 3 = 1040 − 20 = 1020 byte; total data 1480 + 1480 + 1020 = 3980 = 4000 − 20 (header).
- Catatan: IPv6 **tidak** melakukan fragmentation di router (lihat 1.3).

### 8.2 DHCP: Wireshark output (home LAN) (slide 4-49)
**Request (Boot Request, message type 1):**

## 1. Pendahuluan: dua pendekatan control plane

**Network-layer functions:**
- **Forwarding** (data plane): memindahkan packet dari input router ke output router yang tepat.
- **Routing** (control plane): menentukan **route** yang diambil packet dari source ke destination.

**Dua pendekatan menyusun network control plane:**
1. **Per-router control (traditional):** komponen algoritma routing individual di setiap router saling berinteraksi di control plane untuk menghitung forwarding table. Nilai di header packet yang datang → forwarding table → output link (mis. nilai `0111` → output 2).
2. **Logically centralized control (Software-Defined Networking, SDN):** **remote controller** menghitung dan memasang forwarding table di router. Di setiap router ada **CA (control agent)** yang berinteraksi dengan remote controller.

---

## 2. Routing protocols

- **Tujuan routing protocol:** menentukan path ("good" paths = routes) dari sending host ke receiving host, melewati network router.
  - **Path:** urutan router yang dilalui packet dari host asal ke host tujuan.
  - **"Good":** biaya (cost) terkecil, tercepat, paling tidak macet.
  - Routing = salah satu **"top-10" networking challenge**.

### 2.1 Graph abstraction (slide 5-10)
- Graph **G = (N, E)**; **N** = himpunan router; **E** = himpunan link.
- **c(a,b)** = cost link langsung yang menghubungkan a dan b. Contoh: c(w,z) = 5, c(u,z) = ∞ (tidak bertetangga langsung).
- Cost didefinisikan oleh **network operator**: bisa selalu 1, berbanding terbalik dengan bandwidth, atau berbanding terbalik dengan congestion.
- **Graph contoh utama (dipakai di seluruh contoh Dijkstra/Bellman-Ford):** N = {u, v, w, x, y, z}. Cost link: **u–v = 2, u–x = 1, u–w = 5, v–x = 2, v–w = 3, x–w = 3, x–y = 1, w–y = 1, w–z = 5, y–z = 2.**
  - Catatan slide: daftar E di slide tertulis {(u,v),(u,x),(v,x),(v,w),(x,w),(x,y),(w,y),(w,z),(y,z)} — link (u,w) tidak tercantum di daftar itu, tapi muncul di tabel Dijkstra sebagai D(w)=5,u pada langkah 0, jadi dianggap ada. **[Catatan]**

### 2.2 Routing algorithm classification (slide 5-11)
- **Global vs decentralized information?**
  - **Global:** semua router punya topologi lengkap & info link cost → algoritma **"link state"**.
  - **Decentralized:** proses iteratif perhitungan + pertukaran info dengan neighbor; router awalnya hanya tahu link cost ke neighbor yang terhubung langsung → algoritma **"distance vector"**.
- **How fast do routes change?**
  - **Dynamic:** route berubah lebih cepat (update periodik atau sebagai respons perubahan link cost).
  - **Static:** route berubah lambat seiring waktu.

## 3. Link-state routing: algoritma Dijkstra (slide 5-13 s.d. 5-30)

### 3.1 Sifat
- **Centralized:** topologi network dan link cost diketahui semua node, lewat **"link state broadcast"**; semua node punya info yang sama.
- Menghitung **least cost path dari satu node ("source") ke semua node lain** → menghasilkan **forwarding table** untuk node itu.
- **Iterative:** setelah k iterasi, diketahui least cost path ke k destination.

### 3.2 Notasi
- `c(x,y)`: cost link langsung dari x ke y; = ∞ jika bukan neighbor langsung.
- `D(v)`: estimasi cost least-cost-path saat ini dari source ke destination v.
- `p(v)`: **predecessor** node sepanjang path dari source ke v.
- `N'`: himpunan node yang least-cost-path-nya sudah **definitif** diketahui.

### 3.3 Algoritma
```
1  Initialization:
2    N' = {u}                      /* compute least cost path from u to all other nodes */
3    for all nodes v
4      if v adjacent to u          /* u initially knows direct-path-cost only to direct neighbors */
5        then D(v) = c(u,v)        /* but may not be minimum cost! */
6      else D(v) = ∞
7
8  Loop
9    find w not in N' such that D(w) is a minimum
10   add w to N'
11   update D(v) for all v adjacent to w and not in N':
12     D(v) = min( D(v), D(w) + c(w,v) )
13     /* new least-path-cost to v is either old least-cost-path to v or known
14        least-cost-path to w plus direct-cost from w to v */
15 until all nodes in N'
```

### 3.4 Contoh 1: source = u (graph di 2.1)
| Step | N' | D(v),p(v) | D(w),p(w) | D(x),p(x) | D(y),p(y) | D(z),p(z) |
|---|---|---|---|---|---|---|
| 0 | u | 2,u | 5,u | **1,u** | ∞ | ∞ |
| 1 | ux | **2,u** | 4,x | | 2,x | ∞ |
| 2 | uxy | **2,u** (dipilih) | 3,y | | | 4,y |
| 3 | uxyv | | **3,y** | | | 4,y |
| 4 | uxyvw | | | | | **4,y** |
| 5 | uxyvwz | | | | | |

Perhitungan yang ditulis di slide:
- Step 1 (tambah x): D(v) = min(2, 1+2) = 2; D(w) = min(5, 1+3) = 4; D(y) = min(∞, 1+1) = 2.
- Step 2 (tambah y): D(w) = min(4, 2+1) = 3; D(z) = min(∞, 2+2) = 4.

- Step 4 (tambah w): D(z) = min(4, 3+5) = 4.

**Hasil: least-cost-path tree dari u** (dibangun dengan menelusuri predecessor): u→v langsung; u→x; x→y; y→w; y→z.
- **Forwarding table di u:**

### 3.6 Diskusi Dijkstra (slide 5-29)
- **Algorithm complexity** (n node): tiap dari n iterasi harus cek semua node w yang belum di N → total **n(n+1)/2 perbandingan → O(n²)**. Implementasi lebih efisien mungkin: **O(n log n)**.
- **Message complexity:** tiap router harus **broadcast** info link state ke router lain. Algoritma broadcast efisien: **O(n) link crossings** untuk menyebarkan satu pesan broadcast dari satu sumber. Pesan tiap router melewati O(n) link → total **O(n²)** message.

### 3.7 Oscillations (slide 5-30)
- Jika **link cost bergantung pada volume traffic**, bisa terjadi **route oscillation**.
- Skenario contoh: routing ke destination **a**, traffic masuk di d, c, e dengan rate **1, e (<1), 1**; **link cost bersifat directional dan bergantung volume**. Node: a, b, c, d. Rute berpindah bolak-balik: tiap kali traffic pindah ke path lain, cost path itu naik dan cost path lama turun, sehingga di iterasi berikutnya traffic pindah lagi (initially → "given these costs, find new routing... resulting in new costs" berulang).

## 4. Distance vector algorithm (slide 5-32 s.d. 5-52)

### 4.1 Bellman-Ford equation (dynamic programming)
- Misal **Dx(y)** = cost least-cost path dari x ke y. Maka:
  **Dx(y) = min over v { c(x,v) + Dv(y) }**
  - min diambil atas **semua neighbor v dari x**
  - `c(x,v)` = cost link langsung x ke v
  - `Dv(y)` = estimasi v untuk cost least-cost-path ke y
- **Node yang mencapai minimum = next hop** pada estimated least-cost path ke destination.

**Contoh Bellman-Ford (slide 5-33):** neighbor u: x, v, w. Untuk destination z: Dv(z) = 5, Dw(z) = 3, Dx(z) = 3.
- Du(z) = min{ c(u,v) + Dv(z), c(u,x) + Dx(z), c(u,w) + Dw(z) } = min{ 2+5, 1+3, 5+3 } = **4**.
- Node yang mencapai minimum (**x**) = next hop pada estimated least-cost path ke z.

### 4.2 Ide kunci
- Dari waktu ke waktu, tiap node mengirim **distance vector (DV) estimate**-nya sendiri ke neighbors.
- Dalam kondisi minor yang natural, estimasi Dx(y) **konvergen** ke least cost sebenarnya dx(y).
- Saat x menerima DV baru dari neighbor mana pun, ia meng-update DV-nya dengan B-F equation: **Dx(y) ← min_v { c(x,v) + Dv(y) }** untuk setiap node y ∈ N.

### 4.3 Sifat algoritma DV
- **Iterative, asynchronous:** tiap iterasi lokal dipicu oleh (a) perubahan link cost lokal, atau (b) pesan DV update dari neighbor.
- **Distributed, self-stopping:** tiap node memberi tahu neighbor **hanya ketika DV-nya berubah**; neighbor lalu memberi tahu neighbor mereka — hanya jika perlu. Tidak ada notifikasi → tidak ada aksi.
- Loop tiap node: **wait** (for change in local link cost or msg from neighbor) → **recompute** DV estimates memakai DV dari neighbor → **if DV to any destination has changed, notify neighbors**.

### 4.4 Contoh DV besar: grid 9 node a–i (slide 5-36 s.d. 5-48)
**Topologi (diturunkan dari gambar & isi tabel; semua cost 1 kecuali yang disebut):**
- Baris atas: a, b, c; tengah: d, e, f; bawah: g, h, i.
- Link: a–b (**cost 8**, "larger cost"), b–c, a–d, b–e, d–e, e–f, d–g, e–h, f–i, g–h, h–i. **Tidak ada link c–f** ("missing link"). Slide menyebut: "A few asymmetries: missing link, larger cost". **[Diturunkan]**

**t=0:** semua node punya estimasi jarak ke neighbor terdekat saja; semua node mengirim DV lokal ke neighbors.
- DV di a: Da(a)=0, Da(b)=8, Da(d)=1, sisanya ∞.
- DV di b (t=0): Db(a)=8, Db(c)=1, Db(e)=1, sisanya ∞.
- DV di c (t=0): Dc(b)=1, Dc(c)=0, sisanya ∞.
- DV di e (t=0): De(b)=1, De(d)=1, De(f)=1, De(h)=1, De(e)=0, sisanya ∞.

**Tiap iterasi (t=1, 2, ...), semua node:** (1) menerima DV dari neighbors, (2) menghitung DV lokal baru, (3) mengirim DV baru ke neighbors.

**Komputasi di b pada t=1 (b menerima DV dari a, c, e):**
- Db(a) = min{ c(b,a)+Da(a), c(b,c)+Dc(a), c(b,e)+De(a) } = min{8, ∞, ∞} = **8**

- Db(e) = min{ ∞, ∞, 1 } = **1**
- Db(g) = min{ ∞, ∞, ∞ } = **∞**

**Komputasi di c pada t=1 (c hanya menerima DV dari b):**

### 4.5 State information diffusion (slide 5-49)
Komunikasi + komputasi iteratif menyebarkan informasi melalui network. State c pada t=0:
- t=0: state c hanya ada di c.
- t=1: sudah menyebar ke b; bisa memengaruhi komputasi DV sejauh **1 hop** (di b).
- t=2: sejauh **2 hop** (b, dan a, e).
- t=3: sejauh **3 hop** (d, f, h).
- t=4: sejauh **4 hop** (g, i).

### 4.6 Perubahan link cost (slide 5-50, 5-51)
Topologi: x–y cost **4**, y–z cost **1**, x–z cost **50**.

**Good news travels fast** (cost link y–x turun, mis. dari 4 jadi 1):
- t0: y mendeteksi perubahan link cost, update DV-nya, memberi tahu neighbors.
- t1: z menerima update dari y, update DV, menghitung least cost baru ke x, kirim DV-nya ke neighbors.
- t2: y menerima update z, update DV. Least cost y tidak berubah → **y tidak mengirim pesan ke z**. Selesai.

**Bad news travels slow — count-to-infinity problem** (cost link y–x naik jadi **60**):
- y melihat link langsung ke x kini bercost 60, tapi z sudah bilang punya path bercost 5. Maka y menghitung: "cost baruku ke x = **6**, via z" → memberi tahu z cost 6.
- z belajar bahwa path ke x via y kini 6, jadi z menghitung "cost baruku ke x = **7** via y" → memberi tahu y.
- y belajar cost via z = 7 → y hitung **8** → beri tahu z.
- z belajar 8 → hitung **9** → beri tahu y.
- ... berulang (loop) naik satu-satu. "See text for solutions. Distributed algorithms are tricky!"

### 4.7 Contoh DV tambahan: tiga node x, y, z (slide 5-120, 5-121)
Link: **x–y = 2, x–z = 7, y–z = 1.**

**Inisialisasi (t=0), tabel DV tiap node (cost to x,y,z):**
| Node | to x | to y | to z |
|---|---|---|---|
| Dx | 0 | 2 | 7 |
| Dy | 2 | 0 | 1 |
| Dz | 7 | 1 | 0 |

- Dx(z) = min{ c(x,y)+Dy(z), c(x,z)+Dz(z) } = min{ 2+1, 7+0 } = **3**

**Hasil konvergen (stabil):**

## 5. Perbandingan LS vs DV (slide 5-52)
| Aspek | **Link State (LS)** | **Distance Vector (DV)** |
|---|---|---|
| **Message complexity** | n router → **O(n²)** messages dikirim | Pertukaran antar **neighbors saja**; waktu konvergensi bervariasi |
| **Speed of convergence** | **O(n²)** algorithm, O(n²) messages; **bisa terjadi oscillations** | Waktu konvergensi **bervariasi**; **bisa terjadi routing loops**; **count-to-infinity problem** |
| **Robustness** (router malfunction / compromised) | Router bisa mengiklankan **link cost yang salah**; tiap router hanya menghitung **tabelnya sendiri** | Router DV bisa mengiklankan **path cost salah** ("I have a really low-cost path to everywhere") → **black-holing**; DV tiap router dipakai router lain → **error menyebar** lewat network |

## 6. Scalable routing: Autonomous System (AS) (slide 5-53 s.d. 5-58)

### 6.1 Kenapa perlu hierarchy
Studi routing sejauh ini **idealisasi**: semua router identik, network "flat" — tidak benar di praktik.
- **Scale:** miliaran destination → tidak bisa menyimpan semua destination di routing table; pertukaran routing table akan membanjiri link.
- **Administrative autonomy:** Internet = "network of networks"; tiap admin network ingin mengontrol routing di networknya sendiri.

### 6.2 Pendekatan Internet
- Router dikelompokkan dalam wilayah yang disebut **autonomous systems (AS)** (alias **"domains"**).
- **Intra-AS (intra-domain):** routing di antara router dalam AS yang sama.
  - Semua router dalam AS **harus menjalankan protokol intra-domain yang sama**.
  - Router di AS berbeda **boleh** menjalankan protokol intra-domain berbeda.
  - **Gateway router:** di "edge" AS-nya, punya link ke router di AS lain.
- **Inter-AS (inter-domain):** routing di antara AS. **Gateway** melakukan inter-domain routing (selain intra-domain).

### 6.3 Interconnected ASes (slide 5-56)
- Contoh: AS1 (router 1a, 1b, 1c, 1d), AS2 (2a, 2b, 2c, 2d), AS3 (3a, 3b, 3c, 3d). Tiap AS menjalankan intra-AS routing sendiri; antar AS dijalankan inter-AS routing.
- **Forwarding table dikonfigurasi oleh algoritma intra- dan inter-AS:**
  - Intra-AS routing menentukan entry untuk **destination di dalam AS**.
  - Inter-AS **dan** intra-AS menentukan entry untuk **destination eksternal**.

### 6.4 Peran inter-AS routing dalam forwarding intra-domain (slide 5-57)
Jika router di AS1 menerima datagram dengan tujuan di luar AS1, inter-domain routing AS1 harus:
1. **Mempelajari** destination mana yang reachable lewat AS2 dan mana lewat AS3.
2. **Menyebarkan** info reachability ini ke semua router di AS1.
- Router harus forward packet ke gateway router di AS1 — **tapi gateway yang mana?**

## 7. Intra-AS routing & OSPF (slide 5-58 s.d. 5-60)

### 7.1 Protokol intra-AS paling umum
| Protokol | Keterangan |
|---|---|
| **RIP** — Routing Information Protocol [RFC 1723] | Classic **DV**; DV dipertukarkan tiap **30 detik**; **tidak lagi banyak dipakai** |
| **EIGRP** — Enhanced Interior Gateway Routing Protocol | **DV-based**; selama puluhan tahun **proprietary Cisco**, menjadi open pada 2013 [RFC 7868] |
| **OSPF** — Open Shortest Path First [RFC 2328] | **Link-state routing**. **IS-IS** (standar ISO, bukan standar RFC) pada dasarnya sama dengan OSPF |

### 7.2 OSPF
- **"Open"** = tersedia untuk publik.
- **Classic link-state:**
  - Tiap router **flood OSPF link-state advertisements** (langsung di atas **IP**, bukan TCP/UDP) ke semua router lain dalam seluruh AS.
  - Mendukung **banyak metrik link cost**: bandwidth, delay.
  - Tiap router punya **topologi penuh**, memakai **algoritma Dijkstra** untuk menghitung forwarding table.
- **Security:** semua pesan OSPF **diautentikasi** (mencegah intrusi berbahaya).

### 7.3 Hierarchical OSPF (slide 5-60)
- **Two-level hierarchy: local area dan backbone.**
  - Link-state advertisements di-flood **hanya di dalam area, atau backbone**.
  - Tiap node punya topologi detail **area**-nya; hanya tahu **arah** untuk mencapai destination lain.
- Peran router:
  - **Area border routers:** "meringkas" (summarize) jarak ke destination di areanya sendiri, lalu mengiklankannya di backbone.
  - **Backbone routers:** menjalankan OSPF terbatas di backbone.
  - **Boundary router:** terhubung ke AS lain.
  - **Local (internal) routers:** flood LS hanya di dalam area; hitung routing dalam area; forward packet ke luar area lewat area border router.
- Contoh: area 1, area 2, area 3 terhubung ke backbone.

## 8. BGP — Border Gateway Protocol (slide 5-61 s.d. 5-75)

### 8.1 Peran BGP
- **BGP** = protokol inter-domain routing **de facto** — **"glue that holds the Internet together"**.
- Memungkinkan subnet mengiklankan keberadaannya & destination yang dapat dijangkau ke seluruh Internet: **"I am here, here is who I can reach, and how"**.
- BGP memberi tiap AS cara untuk:
  - **eBGP:** mendapat info reachability destination network dari AS tetangga.
  - Menentukan route ke network lain berdasarkan info reachability **dan policy**.
  - **iBGP:** menyebarkan info reachability ke semua router internal AS.
  - **Advertise** info reachability destination ke network tetangga.

### 8.2 eBGP & iBGP connections (slide 5-64)
- **eBGP connectivity** = antar gateway router di AS berbeda; **logical iBGP connectivity** = antar router dalam AS yang sama.
- **Gateway routers menjalankan eBGP dan iBGP.**
- Contoh: AS1, AS2, AS3 dengan gateway 1c, 2a/2c, 3a, dst.

### 8.3 BGP basics (slide 5-65)
- Ketika gateway AS3 **3a** mengiklankan path **"AS3, X"** ke gateway AS2 **2c**: **AS3 berjanji ke AS2** akan meneruskan datagram menuju X.
- **BGP session:** dua BGP router ("peers") bertukar **BGP messages** lewat koneksi **TCP semi-permanen**:
  - Mengiklankan **path** ke berbagai destination network prefix (BGP = **"path vector" protocol**).

### 8.4 BGP messages (slide 5-66) [RFC 4371]
| Pesan | Fungsi |
|---|---|
| **OPEN** | Membuka koneksi TCP ke remote BGP peer dan mengautentikasi sending BGP peer |
| **UPDATE** | Mengiklankan path baru (atau **menarik/withdraw** path lama) |
| **KEEPALIVE** | Menjaga koneksi tetap hidup saat tidak ada UPDATE; juga **ACK** untuk OPEN request |
| **NOTIFICATION** | Melaporkan error pada pesan sebelumnya; juga dipakai untuk **menutup koneksi** |

### 8.4b Path attributes & BGP routes (slide 5-67)
- **BGP advertised route = prefix + attributes.**
  - **Prefix:** destination yang diiklankan.
  - Dua atribut penting:
    - **AS-PATH:** daftar AS yang dilewati advertisement prefix.
    - **NEXT-HOP:** menunjukkan router internal-AS spesifik menuju next-hop AS.
- **Policy-based routing:**
  - Gateway yang menerima route advertisement memakai **import policy** untuk menerima/menolak path (mis. "never route through AS Y").
  - **AS policy** juga menentukan apakah path diiklankan ke AS tetangga lain.

### 8.5 BGP path advertisement (slide 5-68, 5-69)
Contoh dengan destination **X** di AS3:
1. Router AS2 **2c** menerima advertisement **"AS3, X"** (via eBGP) dari router AS3 **3a**.
2. Berdasarkan policy AS2, **2c menerima path AS3,X** dan menyebarkannya (via **iBGP**) ke semua router AS2.
3. Berdasarkan policy AS2, router **2a** mengiklankan (via eBGP) path **"AS2, AS3, X"** ke router AS1 **1c**.

**Multiple paths:** gateway bisa belajar beberapa path ke destination.
- Gateway AS1 **1c** belajar path **AS2,AS3,X** dari 2a **dan** path **AS3,X** dari 3a.
- Berdasarkan policy, 1c **memilih AS3,X** dan mengiklankannya dalam AS1 via **iBGP**.

### 8.6 BGP: populating forwarding tables (slide 5-70, 5-71)
- 1a, 1b, 1d belajar via iBGP dari 1c: **"path to X goes through 1c"**.
- **Di 1d:** OSPF intra-domain routing: untuk mencapai 1c pakai **interface 1** → entry forwarding table: `1c → 1`, **`X → 1`** (untuk mencapai X pakai interface 1).
- **Di 1a:** OSPF: untuk mencapai 1c pakai **interface 2** → `1c → 2`, **`X → 2`**.
- Jadi forwarding entry untuk destination eksternal (X) = entry untuk next-hop gateway (dari **OSPF**), dikombinasi info dari **iBGP/eBGP**.

### 8.7 Hot potato routing (slide 5-72)
- 2d belajar (via iBGP) bahwa ia bisa route ke X lewat **2a atau 2c**.
- **Hot potato routing:** pilih **local gateway dengan intra-domain cost terkecil** (mis. **2d memilih 2a**, meskipun lebih banyak AS hop ke X): **tidak peduli inter-domain cost!**
- Di slide: AS1,AS3,X dan AS3,X sebagai path; OSPF link weights di gambar bernilai 201, 112, 263.

### 8.8 Achieving policy via advertisements (slide 5-73, 5-74)
**Legend:** A, B, C = **provider networks**; w, x, y = **customer networks**.

**Contoh 1 (slide 5-73):**
- A mengiklankan path **Aw** ke B dan ke C.
- **B memilih TIDAK mengiklankan BAw ke C!** B tidak mendapat "revenue" untuk routing C→B→A→w, karena C, A, maupun w bukan customer B.
- C tidak belajar path CBAw → C akan route **CAw** (tanpa B) untuk ke w.
- **Policy dunia nyata tipikal:** ISP hanya mau route traffic **dari/ke customer networks-nya** (tidak mau membawa **transit traffic** antar ISP lain).

**Contoh 2 (slide 5-74):**
- A, B, C = provider; x, w, y = customer; **x dual-homed** (terhubung ke dua network).
- **Policy:** x tidak mau route dari B ke C lewat x → **x tidak akan mengiklankan ke B route ke C.**

### 8.9 BGP route selection (slide 5-75)
Router bisa mempelajari >1 route ke destination AS; memilih berdasarkan urutan:
1. **Local preference** value attribute: keputusan **policy**.
2. **Shortest AS-PATH**.
3. **Closest NEXT-HOP router** (**hot potato routing**).
4. Kriteria tambahan.

### 8.10 Kenapa intra- dan inter-AS routing berbeda? (slide 5-76)
| Aspek | Inter-AS | Intra-AS |
|---|---|---|
| **Policy** | Admin ingin kontrol atas bagaimana traffic-nya di-route dan siapa yang route lewat networknya | Satu admin → policy kurang jadi isu |
| **Scale** | Hierarchical routing menghemat ukuran table, mengurangi traffic update | (sama) |
| **Performance** | **Policy mendominasi** atas performance | Bisa fokus ke **performance** |

## 9. SDN control plane (slide 5-77 s.d. 5-100)

### 9.1 Latar belakang
- Network layer Internet secara historis diimplementasikan lewat **pendekatan distributed, per-router control**:
  - **Router monolitik** berisi hardware switching, menjalankan implementasi **proprietary** protokol standar Internet (IP, RIP, IS-IS, OSPF, BGP) di OS router proprietary (mis. **Cisco IOS**).
  - Berbagai **"middleboxes"** untuk fungsi network layer berbeda: firewalls, load balancers, NAT boxes, ...
- **~2005:** minat baru untuk **memikirkan ulang network control plane**.

### 9.2 Per-router vs SDN control plane
- **Per-router control plane:** komponen algoritma routing individual di tiap router berinteraksi di control plane untuk menghitung forwarding table.
- **SDN control plane:** **remote controller** menghitung & memasang forwarding table di router.

### 9.3 Kenapa logically centralized control plane?
- **Network management lebih mudah:** menghindari misconfiguration router; fleksibilitas lebih besar pada traffic flow.
- **Table-based forwarding** (OpenFlow API) memungkinkan **"programming" router**:
  - **Centralized programming** lebih mudah: hitung table secara terpusat lalu distribusikan.
  - **Distributed programming** lebih sulit: table dihitung sebagai hasil algoritma terdistribusi (protokol) di tiap router.
- **Implementasi control plane yang open (non-proprietary)** → mendorong **inovasi: "let 1000 flowers bloom"**.

### 9.4 Analogi SDN: revolusi mainframe → PC (slide 5-82)
| | Mainframe (sebelum) | PC (sesudah) |
|---|---|---|
| Struktur | **Vertically integrated**, specialized OS + specialized hardware + specialized applications | **Horizontal**, **open interfaces** |
| Sifat | Closed, proprietary, **inovasi lambat**, industri kecil | **Inovasi cepat**, industri besar |
| Komponen | Specialized hardware, specialized OS, apps | Microprocessor (open interface) → OS (Windows / Linux / Mac OS) (open interface) → apps |
Analoginya: jaringan juga dibuka dari yang vertically integrated (switch hardware + OS + apps dari satu vendor) menjadi horizontal dengan open interface. (Slide courtesy: N. McKeown)

### 9.5 Traffic engineering sulit dengan traditional routing (slide 5-83 s.d. 5-85)
Memakai graph contoh (u, v, w, x, y, z):
- **Q:** bagaimana jika operator ingin traffic u→z mengalir lewat **uvwz** (bukan uxyz)? **A:** harus **mendefinisikan ulang link weights** agar algoritma routing menghitung route yang diinginkan (atau butuh algoritma routing baru). **Link weights = satu-satunya "knob" kontrol** → kontrol terbatas.
- **Q:** bagaimana jika operator ingin **membagi** traffic u→z lewat uvwz **dan** uxyz (**load balancing**)? **A:** **tidak bisa** (atau butuh algoritma routing baru).
- **Q:** bagaimana jika w ingin route traffic **biru dan merah** secara berbeda dari w ke z? **A:** **tidak bisa** (dengan destination-based forwarding dan routing LS, DV).
- Pelajaran dari Chapter 4: **generalized forwarding dan SDN** dapat dipakai untuk mencapai routing apa pun yang diinginkan.

### 9.6 Arsitektur SDN (slide 5-86 s.d. 5-90)
**Empat ciri utama:**
1. **Generalized "flow-based" forwarding** (mis. OpenFlow).
2. **Pemisahan control plane dan data plane.**
3. **Fungsi control plane eksternal** terhadap data-plane switches.
4. **Programmable control applications.**

**Tiga lapisan:**
- **Data-plane switches (SDN-controlled switches):**
  - Switch cepat, sederhana, commodity yang mengimplementasikan generalized data-plane forwarding di hardware.
  - Flow (forwarding) table dihitung & dipasang di bawah supervisi controller.
  - **API** untuk kontrol switch berbasis table (mis. OpenFlow): mendefinisikan apa yang bisa/tidak bisa dikontrol.
  - **Protokol** untuk berkomunikasi dengan controller (mis. OpenFlow).
- **SDN controller ("network operating system"):**
  - Memelihara **network state information**.
  - Berinteraksi dengan network-control apps "di atas" lewat **northbound API**.
  - Berinteraksi dengan network switches "di bawah" lewat **southbound API**.
  - Diimplementasikan sebagai **sistem terdistribusi** untuk performance, scalability, fault-tolerance, robustness.
- **Network-control applications:**
  - "**Brains**" dari control: mengimplementasikan fungsi kontrol memakai layanan level lebih rendah & API yang disediakan SDN controller.
  - **Unbundled**: bisa disediakan pihak ketiga, berbeda dari vendor routing atau SDN controller. Contoh app: routing, access control, load balance, ...

**Komponen SDN controller (slide 5-90):**
- **Interface layer ke network control apps** (abstractions API): RESTful API, network graph, intent.
- **Network-wide distributed, robust state management:** state dari link, switch, layanan → **distributed database** (link-state info, host info, switch info, statistics, flow tables, ...).
- **Communication layer** antara SDN controller dan controlled switches: OpenFlow, SNMP, ...

### 9.7 OpenFlow protocol (slide 5-91 s.d. 5-93)
- Beroperasi **antara controller dan switch**; memakai **TCP** untuk pertukaran pesan (**enkripsi optional**).
- **Tiga kelas** pesan OpenFlow: **controller-to-switch**, **asynchronous (switch to controller)**, **symmetric (misc.)**.
- Dibedakan dari **OpenFlow API** (API dipakai untuk menentukan generalized forwarding actions).

**Key controller-to-switch messages:**
| Pesan | Fungsi |
|---|---|
| **features** | Controller query switch features, switch membalas |
| **configure** | Controller query/set parameter konfigurasi switch |
| **modify-state** | Tambah, hapus, ubah flow entry di OpenFlow table |
| **packet-out** | Controller dapat mengirim packet ini keluar dari port spesifik di switch tertentu |

**Key switch-to-controller messages:**
| Pesan | Fungsi |
|---|---|
| **packet-in** | Transfer packet (dan control-nya) ke controller (lihat packet-out dari controller) |
| **flow-removed** | Flow table entry dihapus di switch |
| **port status** | Memberi tahu controller tentang perubahan pada sebuah port |

- Operator network **tidak** "memprogram" switch dengan membuat/mengirim pesan OpenFlow langsung; mereka memakai **abstraksi level lebih tinggi di controller**.

### 9.8 SDN: contoh interaksi control/data plane (slide 5-94, 5-95)
Switch s1, s2, s3, s4. Link failure di s1.
1. **s1** mengalami link failure → memakai pesan OpenFlow **port status** untuk memberi tahu controller.
2. **SDN controller** menerima pesan OpenFlow, **meng-update info link status**.
3. Aplikasi **Dijkstra's routing** yang sebelumnya sudah register untuk dipanggil setiap link status berubah → **dipanggil**.
4. Aplikasi Dijkstra mengakses info network graph & link state di controller, **menghitung route baru**.
5. Aplikasi link-state routing berinteraksi dengan **flow-table-computation component** di SDN controller, yang menghitung flow table baru yang dibutuhkan.
6. Controller memakai **OpenFlow** untuk **memasang table baru** di switch yang perlu di-update.

### 9.9 ONOS SDN controller (slide 5-96)
- **ONOS** = SDN controller open-source awal yang berpengaruh.
- Arsitektur: **Network Applications** (Traffic Engineering, Firewalling, Load Balancing, ...) → **Northbound API** (northbound abstractions & protocols: **REST API**, **Intent**) → **ONOS distributed core** (devices, links, hosts, paths, flow rules, topology, statistics) → **Southbound API** (southbound abstractions & protocols: **OpenFlow, Netconf, OVSDB**; abstraksi device, link, host, flow, packet).
- Poin penting:
  - **Control apps terpisah dari controller.**
  - **Intent framework:** spesifikasi level tinggi dari service — **what** bukan **how**.
  - Penekanan besar pada **distributed core**: reliabilitas layanan, replikasi, performance scaling.
- **Catatan:** slide juga menyebut ODL (OpenDaylight) sebagai controller contoh di summary (Chapter summary: "implementation in practice: ODL, ONOS").

### 9.10 Google ORION SDN control plane (slide 5-97, 5-98)
- **ORION** = SDN control plane Google (NSDI'21) untuk **datacenter (Jupiter)** dan **wide area (B4)** network Google.
- Arsitektur: **routing (intradomain, iBGP)** dan **traffic engineering** diimplementasikan sebagai **aplikasi di atas ORION core**; **edge-edge flow-based controls** (mis. CoFlow scheduling) untuk memenuhi contract SLAs; **management:** pub-sub distributed microservices di Orion core, **OpenFlow** untuk signaling/monitoring switch.
- Catatan: ORION menyediakan layanan **intradomain** dalam network Google.
- **Nilai logically-centralized abstraction** (kutipan Amin Vahdat, Google): karena lokasi dan peran setiap elemen network diketahui sebelumnya (satu gedung / private global WAN), tidak perlu membiarkan node boot, bertukar pesan, dan belajar perannya; peran semua elemen dikonfigurasi di **controller yang logically centralized** yang lalu memberi tahu semua elemen terkait konfigurasi baru/berubah. Ini **menggeser masalah network management dari mengelola konfigurasi elemen individual menjadi mengelola konfigurasi sebuah logical network**, menyederhanakan masalah dari sisi teknis dan dari sisi **cognitive load** network manager.

### 9.11 SDN: selected challenges & masa depan (slide 5-99, 5-100)
**Challenges:**
- **Hardening control plane:** sistem terdistribusi yang dependable, reliable, performance-scalable, secure.
  - Robust terhadap failure: manfaatkan teori kuat sistem terdistribusi reliable.
  - Dependability, security: "baked in" sejak awal?
- Network & protokol yang memenuhi **mission-specific requirements** (mis. real-time, ultra-reliable, ultra-secure).
- **Internet-scaling:** melampaui satu AS.
- **SDN kritis di jaringan 5G cellular.**

**SDN dan masa depan protokol network tradisional:**
- Forwarding table hasil **SDN-computed vs router-computed** hanyalah satu contoh dari **logically-centralized-computed vs protocol-computed**.
- Bisa dibayangkan **SDN-computed congestion control**: controller menentukan sender rate berdasarkan tingkat congestion yang dilaporkan router.
- Pertanyaan terbuka: bagaimana implementasi fungsionalitas network (SDN vs protokol) akan berevolusi?

## 10. ICMP — Internet Control Message Protocol (slide 4-102 / 4-103 di file W08)

### 10.1 ICMP
- Dipakai host dan router untuk mengomunikasikan **informasi network-level**:
  - **Error reporting:** unreachable host, network, port, protocol.
  - **Echo request/reply** (dipakai oleh **ping**).
- Berada di **network layer "di atas" IP**: pesan ICMP dibawa dalam IP datagram.
- **ICMP message:** **type, code** + 8 byte pertama dari IP datagram yang menyebabkan error.

**Tabel type/code:**
| Type | Code | Deskripsi |
|---|---|---|
| 0 | 0 | echo reply (ping) |
| 3 | 0 | dest. network unreachable |
| 3 | 1 | dest host unreachable |
| 3 | 2 | dest protocol unreachable |
| 3 | 3 | dest port unreachable |
| 3 | 6 | dest network unknown |
| 3 | 7 | dest host unknown |
| 4 | 0 | source quench (congestion control — **tidak dipakai**) |
| 8 | 0 | echo request (ping) |
| 9 | 0 | route advertisement |
| 10 | 0 | router discovery |
| 11 | 0 | **TTL expired** |
| 12 | 0 | bad IP header |

### 10.2 Traceroute dan ICMP
- **Source** mengirim set **UDP segment** ke destination:
  - Set ke-1 punya **TTL = 1**, set ke-2 **TTL = 2**, dst. (**3 probe** per set).
- Datagram di set ke-n tiba di **router ke-n**:
  - Router **membuang datagram** dan mengirim ke source pesan **ICMP (type 11, code 0)** (TTL expired).
  - Pesan ICMP kemungkinan memuat **nama router & IP address**.
- Saat pesan ICMP tiba di source: **catat RTT**.
- **Stopping criteria:**
  - UDP segment akhirnya tiba di **destination host**.
  - Destination mengembalikan ICMP **"port unreachable" (type 3, code 3)**.
  - Source **berhenti**.

## 11. Network management & configuration (slide 5-105 s.d. 5-116)

### 11.1 Apa itu network management?
- **Autonomous systems (alias "network")**: ribuan komponen hardware/software yang berinteraksi.
- Sistem kompleks lain yang butuh monitoring, konfigurasi, kontrol: jet airplane, nuclear power plant, dll.
- Definisi: *"Network management includes the deployment, integration and coordination of the hardware, software, and human elements to monitor, test, poll, configure, analyze, evaluate, and control the network and element resources to meet the real-time, operational performance, and Quality of Service requirements at a reasonable cost."*

### 11.2 Komponen network management (slide 5-106)
| Komponen | Deskripsi |
|---|---|
| **Managing server / controller** | Aplikasi, biasanya dengan **network manager (manusia) in the loop** |
| **Managed device** | Peralatan dengan komponen hardware/software yang dapat dikelola/dikonfigurasi; punya **agent** dan **data** |
| **Data** | "State" device: **configuration data, operational data, device statistics** |
| **Network management protocol** | Dipakai managing server untuk **query, configure, manage** device; dipakai device untuk memberi tahu managing server tentang data dan event |

### 11.3 Pendekatan operator network (slide 5-107)
1. **CLI (Command Line Interface):** operator mengetik/men-script perintah langsung ke device individual (mis. via **ssh**).
2. **SNMP/MIB:** operator query/set data device (**MIB**) memakai **Simple Network Management Protocol**.
3. **NETCONF/YANG:** lebih abstrak, **network-wide, holistik**; penekanan pada **manajemen konfigurasi multi-device**.
   - **YANG:** data modeling language.
   - **NETCONF:** mengomunikasikan aksi/data yang kompatibel dengan YANG ke/dari/antar remote device.

### 11.4 SNMP protocol (slide 5-108 s.d. 5-110)
**Dua cara menyampaikan info MIB dan command:**
- **Request/response mode:** managing server mengirim request ke agent, agent membalas response.
- **Trap mode:** agent mengirim **trap message** secara inisiatif sendiri ke managing server.

**SNMP message types:**
| Message type | Fungsi |
|---|---|
| **GetRequest, GetNextRequest, GetBulkRequest** | Manager→agent: "get me data" (data instance, next data in list, block of data) |
| **SetRequest** | Manager→agent: set MIB value |
| **Response** | Agent→manager: value, respons terhadap Request |
| **Trap** | Agent→manager: memberi tahu manager tentang **exceptional event** |

**SNMP message formats:**
- **SNMP PDU (message types 0–3):** `PDU type (0-3)` | `Request ID` | `Error Status (0-5)` | `Error Index` | lalu pasangan variabel `Name, Value, Name, Value, ...` (Get/set header + variables to get/set).
- **Trap (message type 4):** `PDU type 4` | `Enterprise` | `Agent Addr` | `Trap Type (0-7)` | `Specific code` | `Time stamp` | `Name, Value` (Trap header + trap info).

### 11.5 SNMP: MIB — Management Information Base (slide 5-111)
- Data operasional (dan sebagian konfigurasi) device dikumpulkan dalam **device MIB module**.
  - **~400 MIB modules** didefinisikan di RFC; banyak lagi MIB spesifik vendor.
- **SMI (Structure of Management Information):** data definition language untuk MIB.
- Contoh variabel MIB untuk protokol **UDP:**
  | Object ID | Name | Type | Comments |
  |---|---|---|---|
  | 1.3.6.1.2.1.7.1 | UDPInDatagrams | 32-bit counter | total # datagram yang dikirim ke aplikasi (delivered) |
  | 1.3.6.1.2.1.7.2 | UDPNoPorts | 32-bit counter | # datagram tak terkirim (tidak ada aplikasi di port) |
  | 1.3.6.1.2.1.7.3 | UDPInErrors (di slide tertulis "UDInErrors") | 32-bit counter | # datagram tak terkirim (alasan lain) |
  | 1.3.6.1.2.1.7.4 | UDPOutDatagrams | 32-bit counter | total # datagram dikirim |
  | 1.3.6.1.2.1.7.5 | udpTable | SEQUENCE | satu entry untuk tiap port yang sedang dipakai |

### 11.6 NETCONF (slide 5-112 s.d. 5-115)
- **Tujuan:** secara **aktif mengelola/mengonfigurasi device network-wide**.
- Beroperasi **antara managing server dan managed network devices:**
  - Aksi: **retrieve, set, modify, activate** konfigurasi.
  - **Atomic-commit actions** atas beberapa device.
  - Query **operational data dan statistics**.
  - **Subscribe** ke notifikasi dari device.
- Paradigma **remote procedure call (RPC)**:
  - Pesan protokol NETCONF di-encode dalam **XML**.
  - Dipertukarkan lewat transport **aman dan reliable** (mis. **TLS**).

**NETCONF initialization, exchange, close (slide 5-113):**
- Session initiation & **capabilities exchange: `<hello>`** → serangkaian **`<rpc>` / `<rpc-reply>`** (dan `<notification>`) → session close: **`<close-session>`**.

**Selected NETCONF operations (slide 5-114):**
| Operation | Deskripsi |
|---|---|
| `<get-config>` | Retrieve seluruh/sebagian konfigurasi tertentu. Device bisa punya banyak konfigurasi. |
| `<get>` | Retrieve seluruh/sebagian **configuration state dan operational state data**. |
| `<edit-config>` | Ubah konfigurasi tertentu (mungkin running) di managed device. `<rpc-reply>` device berisi `<ok>` atau `<rpc-error>` dengan **rollback**. |
| `<lock>`, `<unlock>` | Kunci (buka kunci) configuration datastore di managed device (untuk mengunci perintah NETCONF, SNMP, atau CLI dari sumber lain). |
| `<create-subscription>`, `<notification>` | Mengaktifkan langganan event notification dari managed device. |

**Sample NETCONF RPC message (slide 5-115):** RPC XML dengan **message id**; mengubah **running configuration**; contoh: **ubah MTU interface Ethernet 0/0 menjadi 1500** (`<edit-config>`).

### 11.7 YANG (slide 5-116)
- **Data modeling language** untuk menentukan **struktur, sintaks, semantik** data network management NETCONF.
  - Punya **built-in data types**, seperti SMI.
- **Dokumen XML** yang mendeskripsikan device dan capabilities bisa **di-generate dari deskripsi YANG**.
- Bisa mengekspresikan **constraint antar data** yang harus dipenuhi konfigurasi NETCONF yang valid → memastikan konfigurasi NETCONF memenuhi **kriteria correctness dan consistency**.
- Alur: YANG → (generated) XML → pesan RPC NETCONF `<edit-config>` berisi XML hasil generate YANG → agent/device.

## B. Angka & fakta yang sering jadi bahan soal
- IPv6 header **40 byte fixed**, address **128 bit** (8 hextet); IPv4 **32 bit**.
- IPv6: tidak ada checksum, tidak ada fragmentation di router, options → extension headers.
- DHCP: port server **67**, client **68**; lease contoh **3600 secs**; Ethernet dest broadcast **FFFFFFFFFFFF**.
- IPv4 chunk terakhir dialokasikan ICANN ke RRs: **2011**; ada **5 RRs**.
- Contoh blok ISP: **200.23.16.0/20** → 8 blok **/23**.
- Fragmentation 4000 B / MTU 1500 → fragmen 1500 (offset 0), 1500 (offset 185), 1040 (offset 370).
- Dijkstra: **O(n²)** (bisa O(n log n)); LS message complexity **O(n²)**.
- RIP: DV tiap **30 detik**; EIGRP open sejak **2013** (RFC 7868); OSPF RFC **2328**; RIP RFC **1723**.
- BGP messages: **OPEN, UPDATE, KEEPALIVE, NOTIFICATION**; berjalan di atas **TCP**.

## D. Hubungan antar topik (untuk menyusun alur section web)
- IPv6 ↔ NAT ↔ IPv4 exhaustion (NAT & IPv6 sama-sama jawaban atas habisnya IPv4).
- DHCP (host dapat IP) ↔ subnet allocation (network dapat blok dari ISP) ↔ route aggregation.
- Generalized forwarding (match+action) → dasar SDN → control plane terpusat (Part 2 §9).
- Control plane (Part 2) menjawab "bagaimana forwarding/flow table dihitung?" (akhir Chapter 4).
- Routing: LS (OSPF, Dijkstra) vs DV (RIP/Bellman-Ford) → hierarki AS → intra-AS (OSPF) vs inter-AS (BGP).
- ICMP/traceroute memanfaatkan TTL dan UDP; management (SNMP, NETCONF/YANG) melengkapi kontrol network.
